# Report: low-risk speed-ups (not built or run, a reviewer builds)

Paths: `MSC/` = `MediaServiceCore/youtubeapi/src/main/java/com/liskovsoft/youtubeapi/`, `common/` = `common/src/main/java/com/liskovsoft/smartyoutubetv2/common/`.

1. **Cache check before the lock.** `MSC/service/internal/FormatInfoWrapper.kt` `getFormatInfo`: `getCachedFormatInfo` runs first, outside `FormatFetchLock`. On a hit it returns at once. On a miss it takes the lock, and `getFormatInfoLegacy/Innertube` check the cache again under it (that was already the case, so the check is double-checked). `ReloadPlaybackGate.reset(videoId)` only clears the single-use reload token if it belongs to this same video, and it is a volatile write with no lock. A hit never uses the token, and the old code dropped it on a hit too, so I call it on the fast path to keep the behavior identical. Safe: the cache has its own monitor, `isCacheActual` and the 30 min age check still apply, and the same shared object is returned.
2. **Fetch at the click.** `common/app/presenters/PlaybackPresenter.java` `openVideo(Video)` → new `prefetchFormatInfoOnClick`: fire-and-forget `getFormatInfoObserve(videoId)`, with no handle kept, so nothing can cancel it. It is skipped when the player engine is already initialized, when the video is live or upcoming, when `videoId` is null, and for the Shorts auto start. For the auto start I made `BrowsePresenter.isShortsAutoStarted()` public (it is already prefetched there). If the hover prefetch is still running, the click fetch waits on the lock and then hits the cache, so it is not a duplicate network request.
3. **Null-safe error handler.** `VideoLoaderController.loadFormatInfo`: `getPlayer()` is captured once and null-checked. `runFormatErrorAction` still runs.
4. **No cancelled fetches.** `common/misc/MediaServiceManager.java` `disposeActions()` no longer disposes `mFormatInfoAction`. That field is used only by `MediaServiceManager.loadFormatInfo` (the menu presenter and the dead preload), and the browse prefetches have their own disposables. So `initRandomNext` and every `disposeActions()` caller can no longer cancel a fetch that way. I deleted `preloadNextVideoIfNeeded` (it had no callers anywhere). Skipped: `VideoLoaderController.disposeActions()` still disposes its own `mFormatInfoAction`, the player's current load, when a new video replaces it. Without it a stale result could be processed for the wrong video, and removing it needs a videoId guard, which is a bigger change. `MediaServiceManager.loadFormatInfo` also still disposes its previous call (menu only).
5. **Translation languages.** `MSC/videoinfo/V2/VideoInfoService.java`: the background fetch starts only when the cached list is null (no retry for non-null lists with fewer than 100 entries), and a non-null list is always applied to the result. The thread still runs under `FormatFetchLock`, and its re-check inside the lock is now `!= null`. Skipped: "don't start while a foreground fetch is waiting". That needs a waiter counter shared with the wrapper, and the thread already starts only after the running fetch, behind the lock.
6. **Shorts chain without delay.** `VideoLoaderController`: new flag `mCurrentFromPrefetch`, set when `loadFormatInfo` uses the prefetched/queued info and cleared otherwise. `schedulePrefetch` posts `mPrefetchNext` at once in that case, otherwise it keeps the 300 ms delay.
7. **Shorts entry.** `BrowsePresenter`: `prefetchFirstShort` no longer returns when the start is pending. In the feed callback it now runs before `startShortsIfReady` (which sets `mShortsAutoStarted` and would otherwise skip it), so the player waits on the lock or the cache. It then fetches the second Short after the first completes (`prefetchSecondShort`, `findShortAfter`), never cancelled. Check on the device: Rx `getFormatInfoObserve` must call `onComplete` (the focus prefetch already relies on that).
8. **Snapshot bitmap.** `smarttubetv/.../ShortsTransitionOverlay.java`: two alternating `Bitmap`s (`obtainSnapshotBitmap`), reused when the size is unchanged and allocated otherwise. The bitmap shown in `mOut` is never the next PixelCopy target. One residual case: a timed-out copy that completes two swipes later could write into a bitmap that is being shown. That needs more than 150 ms of a stuck copy plus two swipes, and the result is ignored by the swipe id.
9. **Volatile.** `FormatInfoWrapper`: `mTryInnertubeFirst`, `mInnertubeResult.isUnplayable` and `.client` are `@Volatile`. `VideoInfoService`: `mActualInfoType` and `mNextInfoType` are `volatile`.
10. **Timing logs.** New `common/utils/JoTubeTiming.java` (`Log.d`, tag `JoTubeTiming`, ms since the click via `SystemClock.uptimeMillis`). Marks: `click` (in `PlaybackPresenter.openVideo`, regular videos only; Shorts cancel the measurement), `PlaybackFragment.onCreate`, `onEngineInitialized` (`PlaybackPresenter`), `format info received` and `source prepared (openSabr/openDash)` (`VideoLoaderController.processFormatInfo`), `first frame` (`PlaybackFragment` first-frame listener, which also ends the measurement).

Not done (as instructed): items 4, 6, 8, 11, 12, 13 and anything else.
